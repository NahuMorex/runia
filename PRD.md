# PRD-001: Runnia — Software de entrenamiento para running
## Contexto y Problema
Internet se encuentra plagado -más precisamente en redes sociales- de todo tipo de rutinas y planes para realizar un mismo objetivo de entrenamiento, y es normal encontrarte con opiniones diferentes que se contradigan, dificultando saber qué hacer, cuándo y cómo. Se necesita un sistema que, en base a las capacidades físicas del usuario, indique los pasos a seguir con respaldo técnico, permitiendo entrenar con seguridad y sin tenerle temor a lesionarse.
Personas:
- Milena (Corredora novata): tiene pensado correr por primera vez 10 kilómetros, pero nunca corrió. Quiere saber cuáles son los pasos a seguir y cómo prepararse sin lesionarse.
- Mich (Corredor avanzado): no sabe qué tipo de ejercicio hacer para mejorar su velocidad y ritmo. Quiere saber qué rutina seguir según su nivel actual.
- Pepe (Corredor recurrente, nivel intermedio): le molesta salir a correr y que empiece a llover o haga un calor extremo. Le gustaría saber el pronóstico antes y adaptar el tipo de sesión o el horario.

## Objetivos
Luego de que un usuario cargue su perfil (nivel, frecuencia de entrenamiento, distancia objetivo y ritmo actual) y registre el historial de sus sesiones, el sistema genera un plan de entrenamiento semanal y adaptativo, advierte de condiciones climáticas desfavorables y reprograma o sugiere otros horarios. El producto gana si se cumplen estas metas:
- El 100% de los planes entregados cumple los guardarraíles de carga.
- Al menos el 90% de los mensajes diarios se entregan al usuario.
- Al menos el 70% de las semanas con plan vigente tienen al menos 1 sesión registrada. Una semana con plan vigente es aquella para la cual el sistema generó un plan y el usuario no eliminó su perfil.

## Requerimientos Funcionales
- RF-01: El sistema debe registrar nuevos usuarios mediante email y contraseña.
- RF-02a: El sistema debe autenticar usuarios mediante correo electrónico y contraseña emitiendo un token de sesión.
- RF-02b: El sistema debe renovar el token de sesión en cada request autenticado, hasta un máximo de 7 días desde el login.
- RF-03a: El sistema debe permitir cargar el nivel del corredor (novato, intermedio o avanzado), elegido por el propio usuario.
- RF-03b: El sistema debe permitir cargar la frecuencia de entrenamiento deseada, como un entero de 1 a 7 días por semana.
- RF-03c: El sistema debe permitir cargar la distancia objetivo del corredor, de 1 a 42,2 km.
- RF-03d: El sistema debe permitir cargar el ritmo actual del corredor, en formato mm:ss por km, entre 3:00 y 10:00.
- RF-03e: El sistema debe permitir cargar la ciudad del corredor, usada para consultar el clima, como un texto no vacío de hasta 100 caracteres.
- RF-03f: El sistema debe permitir cargar el rango horario preferido de entrenamiento (hora de inicio y hora de fin en formato HH:MM, con el inicio anterior al fin y una duración mínima de 1 hora), en zona horaria de Buenos Aires, Argentina.
- RF-03g: El sistema debe permitir cargar la hora de envío del mensaje diario (formato HH:MM, anterior a la hora de fin del rango horario preferido), en zona horaria de Buenos Aires, Argentina.
- RF-04: El sistema debe validar que existan los datos obligatorios del perfil (nivel, frecuencia, distancia objetivo, ciudad, rango horario preferido, hora de envío del mensaje diario, chat de Telegram vinculado y, si el nivel no es novato, ritmo actual) antes de ejecutar cualquier cálculo de entrenamiento.
- RF-05: El sistema debe consultar el pronóstico meteorológico a la API de clima.
- RF-06a: El sistema debe generar un plan semanal progresivo según el nivel del usuario.
- RF-06b: El sistema debe limitar el aumento del volumen semanal total, medido en km de trote, a un tope del 10% respecto del volumen planificado de la semana anterior. El volumen planificado es el del plan tal como se generó, sin modificaciones por reprogramaciones, posposiciones ni registros de sesiones. Si el plan de la semana anterior fue parcial (generado a mitad de semana), la base es el volumen planificado de la última semana completa del usuario. Las semanas van de lunes a domingo.
- RF-06c: El sistema debe aplicar una semana de descarga cuando el usuario acumula 4 semanas consecutivas con al menos 1 sesión Completada en cada una.
- RF-06d: El sistema debe excluir las sesiones de calidad del plan de un novato salvo que tenga ritmo actual cargado y que cada una de sus últimas 3 semanas cerradas (de lunes a domingo) tenga al menos 1 sesión Completada y ninguna sesión Parcial/Cortada con RPE ≥ 7. Una sesión de calidad es toda sesión con tramos a un ritmo más rápido que el ritmo actual del usuario (ritmo, velocidad o intervalos); toda otra sesión es una sesión suave.
- RF-06e: El sistema debe incluir como máximo una sesión de calidad por semana en los planes de cualquier nivel.
- RF-06f: El sistema debe limitar el ritmo objetivo de las sesiones de calidad respecto del ritmo actual del usuario.
- RF-06g: El sistema debe limitar cada sesión a un tope inicial en km de trote según el nivel (novato 2 km, intermedio 5 km, avanzado 10 km) cuando el usuario no tuvo plan en la semana anterior, o cuando ese plan fue parcial y el usuario no tiene ninguna semana completa previa. El tope semanal inicial es el tope inicial por sesión multiplicado por la frecuencia cargada.
- RF-06h: El sistema debe mantener sin aumento el volumen semanal total respecto del volumen planificado de la semana anterior cuando esa semana no tuvo ninguna sesión Completada.
- RF-06i: El sistema debe limitar los km de trote de cada sesión a la distancia objetivo del usuario.
- RF-07a: Si las condiciones climáticas son desfavorables (probabilidad de lluvia mayor a 60% o temperatura mayor a 32°C, o ambas, tomando el máximo pronosticado dentro del rango horario preferido del día de la sesión), el sistema debe avisar al usuario y, si existe un día alternativo, pedirle confirmación de si realiza la sesión o la reprograma.
- RF-07b: El sistema debe reprogramar la sesión a la alternativa propuesta cuando el usuario elige reprogramarla.
- RF-08: El sistema debe emitir, los días con sesión planificada que no esté en estado "Pospuesta por clima", un mensaje diario conciso con el entrenamiento del día, a la hora definida por el usuario y una vez recibida su respuesta de fatiga, a través de un bot de Telegram.
- RF-09a: El sistema debe permitir al usuario registrar el estado de la sesión planificada para el día (Completada, Parcial/Cortada o Salteada) a través de un endpoint de la API, que el bot de Telegram invoca cuando el usuario registra la sesión desde el chat. Parcial/Cortada significa que empezó la sesión y la dejó por la mitad; Salteada significa que no la empezó.
- RF-09b: El sistema debe exigir el esfuerzo percibido (RPE, escala 1-10) al registrar una sesión Completada o Parcial/Cortada; para una sesión Salteada no se solicita.
- RF-09c: El sistema debe permitir al usuario agregar notas opcionales al registro de una sesión.
- RF-10: El sistema debe permitir al usuario visualizar su cronograma de entrenamiento de la semana en curso, de lunes a domingo (sesiones pasadas, día actual y proyectadas).
- RF-11: El sistema debe permitir al usuario acceder al historial de todas sus sesiones anteriores con su respectivo estado y feedback.
- RF-12: El sistema debe reclasificar a intensidad "suave/recuperación" las sesiones de los dos días de entrenamiento subsiguientes cuando el usuario registre una sesión como Parcial/Cortada con RPE ≥ 7.
- RF-13a: El sistema debe asignar automáticamente el estado "Pospuesta por clima" a una sesión cuando el día original tenga condición climática extrema (temperatura >38°C, tormenta eléctrica, o probabilidad de lluvia >80%, dentro del rango horario preferido) y no exista, en los 3 días siguientes y sin pasar del domingo de la semana en curso, un día alternativo sin condición desfavorable (este estado es asignado por el sistema, no seleccionado por el usuario, y es distinto de los estados de RF-09a).
- RF-13b: El sistema no debe ofrecer como ejecutable una sesión en estado "Pospuesta por clima".
- RF-13c: El sistema no debe recuperar en otro día del plan el volumen de una sesión en estado "Pospuesta por clima".
- RF-13d: El sistema no debe disparar la reclasificación de RF-12 por una sesión en estado "Pospuesta por clima".
- RF-13e: El sistema debe enviar, el día de una sesión en estado "Pospuesta por clima" y a la hora de envío definida por el usuario, un único mensaje que informe la posposición y su motivo climático, sin preguntar el nivel de fatiga.
- RF-13f: El sistema debe incluir en el mensaje de posposición la cantidad de sesiones en estado "Pospuesta por clima" de la semana cuando sean 2 o más.
- RF-14: El sistema debe permitir vincular la cuenta del usuario con su chat de Telegram mediante un código de un solo uso generado por la API. Cada cuenta admite un único chat y cada chat una única cuenta; no existe desvinculación.
- RF-15: El sistema debe preguntar al usuario su nivel de fatiga (escala 1-10), los días con sesión planificada que no esté en estado "Pospuesta por clima", antes de definir la sesión del día.
- RF-16: El sistema debe asignar una sesión de intensidad "suave/recuperación" cuando el usuario reporta fatiga ≥ 8.
- RF-17: El sistema debe permitir al usuario restablecer su contraseña mediante un código de un solo uso enviado por el bot de Telegram vinculado.
- RF-18a: El sistema debe permitir al usuario editar los datos de su perfil.
- RF-18b: El sistema debe aplicar los cambios de nivel, frecuencia, distancia objetivo y ritmo actual a partir del próximo plan generado, sin regenerar el plan vigente.
- RF-18c: El sistema debe aplicar los cambios de ciudad, rango horario preferido y hora de envío a partir del siguiente mensaje diario.
- RF-19: El sistema debe permitir al usuario eliminar de forma definitiva su perfil y todos sus datos, previa advertencia de que la acción no se puede deshacer.
- RF-20: El sistema debe rechazar el cambio de nivel de novato a intermedio o avanzado si alguna de las últimas 3 semanas cerradas (de lunes a domingo) del usuario no tiene al menos 1 sesión Completada o tiene alguna sesión Parcial/Cortada con RPE ≥ 7. El cambio a un nivel inferior no tiene restricciones.
- RF-21: El sistema debe permitir al usuario solicitar la generación del plan de la semana en curso, cuando no tiene uno, mediante un endpoint de la API (POST /plan).
- RF-22: El sistema debe generar automáticamente cada lunes el plan de la semana que comienza para los usuarios con perfil completo y chat de Telegram vinculado.

## Requerimientos No Funcionales
- RNF-01: El tiempo desde que el usuario responde la pregunta de fatiga hasta que Telegram confirma la entrega del mensaje diario, incluyendo la consulta de clima y la llamada a Gemini, no debe superar los 10 segundos en el percentil 95 (p95) con 10 usuarios simultáneos. El tiempo de espera de la respuesta del usuario no se cuenta.
- RNF-02: El sistema debe registrar en formato estructurado (JSON) el 100% de los siguientes eventos: cada llamada al LLM (resumen del prompt y respuesta), cada herramienta invocada (clima, base de datos), cada guardarraíl aplicado con el valor antes y después (tope 10%, descarga, reclasificación), cada asignación de estado del sistema ("Pospuesta por clima"), cada error de servicio externo y cada decisión de alerta o alternativa climática. No se registran contraseñas, tokens ni historiales completos.
- RNF-03: Las contraseñas deben almacenarse con Argon2id, con parámetros mínimos m=19456 KiB, t=2, p=1 (recomendación OWASP).
- RNF-04: La API key del modelo debe tener 0 apariciones en el código y en el repositorio; se lee de la variable de entorno GOOGLE_API_KEY.

## Criterios de Aceptación
- AC-01 (RF-01): Dado un correo no registrado con formato válido y una contraseña de 8 a 128 caracteres, cuando el usuario solicita registrarse, entonces el sistema crea el registro en base de datos y devuelve código HTTP 201.
- AC-02 (RF-01): Dado un correo ya registrado, cuando el usuario solicita registrarse, entonces el sistema responde con código HTTP 409 sin crear un registro nuevo.
- AC-03 (RF-02a): Dado un usuario registrado que envía credenciales correctas al endpoint de login, cuando el sistema las valida, entonces responde con un token de sesión JWT con vencimiento a las 2 horas y código HTTP 200.
- AC-04 (RF-02a): Dado un usuario que envía un correo o contraseña incorrectos al endpoint de login, cuando el sistema intenta autenticarlo, entonces responde con código HTTP 401 Unauthorized sin emitir token.
- AC-05 (RF-02b): Dado un token vigente emitido hace menos de 7 días, cuando el usuario hace un request autenticado válido, entonces la respuesta incluye un token renovado con vencimiento a las 2 horas desde ese momento; con un token emitido originalmente hace 7 días o más, responde HTTP 401.
- AC-06 (RF-03a, RF-03b, RF-03c, RF-03d, RF-03e, RF-03f, RF-03g): Dado un usuario autenticado, cuando envía por PUT /profile datos de perfil válidos (incluido el ritmo actual si su nivel no es novato), entonces el sistema persiste los datos y responde con código HTTP 200.
- AC-07 (RF-03a a RF-03g): Dado un usuario autenticado que envía por PUT /profile algún dato fuera de los valores, rangos o formatos definidos en RF-03a a RF-03g, cuando el sistema lo valida, entonces responde con código HTTP 422 sin persistir ningún cambio.
- AC-08 (RF-03d, RF-04): Dado un usuario con nivel intermedio o avanzado sin ritmo actual cargado, cuando solicita la generación de un plan, entonces el sistema rechaza la solicitud con código HTTP 422 y el mensaje "No hay datos sobre tu ritmo cargados en tu perfil", sin crear ningún plan.
- AC-09 (RF-03a, RF-03b, RF-03c, RF-03e, RF-03f, RF-03g, RF-04): Dado un usuario al que le falta nivel, frecuencia, distancia objetivo, ciudad, rango horario o hora de envío, cuando solicita la generación de un plan, entonces el sistema rechaza la solicitud con código HTTP 422 y el mensaje "No hay datos sobre tu {campo} cargados en tu perfil", sin crear ningún plan.
- AC-10 (RF-03a, RF-03b, RF-03c, RF-03d, RF-04): Dado un usuario con nivel novato sin ritmo actual cargado pero con los demás datos obligatorios completos, cuando solicita la generación de un plan, entonces el sistema genera el plan sin exigir ritmo actual.
- AC-11 (RF-04, RF-14): Dado un usuario sin chat de Telegram vinculado, cuando solicita la generación de un plan, entonces el sistema responde con código HTTP 422 y el mensaje "Tu cuenta no tiene un chat de Telegram vinculado", sin crear ningún plan.
- AC-12 (RF-05, RF-07a): Dado un error de la API de clima (timeout, rate limit o 5xx), cuando el sistema intenta consultar el pronóstico para generar la sesión diaria, entonces registra el fallo en logs en formato estructurado.
- AC-13 (RF-05, RF-07a): Dado un error de la API de clima (timeout, rate limit o 5xx), cuando el sistema intenta consultar el pronóstico para generar la sesión diaria, entonces entrega el plan diario sin ajuste climático y el mensaje contiene el texto "Clima no disponible: seguí las pautas base de ritmo e hidratación."
- AC-14 (RF-06a): Dado un perfil de corredora novata, cuando el sistema genera el plan de entrenamiento, entonces el plan explicita, para cada sesión de la primera semana, bloques alternados de caminata y trote con la distancia en km de cada bloque.
- AC-15 (RF-06a): Dado un perfil de nivel intermedio o avanzado, cuando el sistema genera el plan de entrenamiento, entonces el plan explicita, para cada sesión de calidad, el tiempo objetivo por tramo y el tiempo de recuperación entre tramos.
- AC-16 (RF-06a, RF-22): Dado un error (5xx o rate limit) o una falta de respuesta en 20 segundos de la API de Gemini durante la generación automática del lunes para un usuario con un plan previo, cuando el sistema intenta generar el plan, entonces adopta su último plan válido como plan de la semana en curso (las mismas sesiones, en los mismos días de la semana), lo entrega al usuario por Telegram y el mensaje contiene el texto "Generación de un nuevo plan no disponible: te enviamos tu último plan válido."
- AC-17 (RF-06a, RF-21): Dado un error (5xx o rate limit) o una falta de respuesta en 20 segundos de la API de Gemini, cuando el usuario solicita POST /plan, entonces el sistema responde con código HTTP 503 y el mensaje "No es posible generar un plan en este momento.", sin crear ningún plan.
- AC-17b (RF-06a, RF-22): Dado un error (5xx o rate limit) o una falta de respuesta en 20 segundos de la API de Gemini durante la generación automática del lunes para un usuario sin ningún plan previo, cuando el sistema intenta generar el plan, entonces envía por Telegram el mensaje "No es posible generar un plan en este momento.", sin crear ningún plan.
- AC-18 (RF-06b): Dado un plan generado por el agente que incrementa el volumen semanal total en más de 10% respecto al volumen planificado de la semana anterior, cuando el sistema aplica el guardarraíl de carga, entonces recorta el plan al tope de 10% antes de entregarlo al usuario, sin ningún piso mínimo que lo supere. Solo los km de trote cuentan en el volumen semanal; los km de caminata no.
- AC-19a (RF-06c): Dado un usuario con al menos 1 sesión Completada en cada una de 4 semanas consecutivas, cuando el sistema genera la semana 5, entonces reduce el volumen total entre 20% y 30% respecto al volumen planificado de la semana 4.
- AC-19b (RF-06c): Dado un usuario con una racha de semanas consecutivas con al menos 1 sesión Completada, cuando cierra una semana sin ninguna sesión Completada, entonces la racha vuelve a 0. La primera semana del plan, aunque sea parcial, cuenta para la racha si tiene al menos 1 sesión Completada.
- AC-19c (RF-06c): Dado un usuario que terminó una semana de descarga, cuando el sistema cuenta las semanas consecutivas para la próxima descarga, entonces el conteo empieza de 0 a partir de la semana siguiente a la descarga.
- AC-19d (RF-06c, RF-06b): Dado un usuario que terminó una semana de descarga (semana 5), cuando el sistema genera la semana 6, entonces el volumen total de la semana 6 iguala el volumen planificado de la semana 4, exento del tope de AC-18. "Igualar" refiere al volumen total, no necesariamente a las mismas sesiones. Si la semana de descarga no tuvo ninguna sesión Completada, prevalece AC-63 y la semana 6 no supera el volumen planificado de la semana 5.
- AC-20 (RF-06d): Dado un perfil novato que no tiene ritmo actual cargado, o que en alguna de sus últimas 3 semanas cerradas no tiene al menos 1 sesión Completada o tiene alguna sesión Parcial/Cortada con RPE ≥ 7, cuando el sistema genera el plan semanal, entonces el plan no incluye ninguna sesión de calidad. La primera semana del plan, aunque sea parcial, cuenta si tiene al menos 1 sesión Completada.
- AC-21 (RF-06e): Dado un perfil de cualquier nivel, cuando el sistema genera el plan semanal, entonces incluye como máximo una sesión de calidad por semana.
- AC-22 (RF-06f): Dado un ritmo actual cargado por el usuario, cuando el sistema genera una sesión de calidad, entonces el ritmo objetivo sugerido está entre el ritmo actual y ese ritmo reducido un 5,6% (por ejemplo, con 6:00 min/km, entre 6:00 y 5:40 min/km).
- AC-23 (RF-05, RF-07a): Dado un pronóstico cuyo máximo dentro del rango horario preferido del día de la sesión es probabilidad de lluvia >60% o temperatura >32°C, cuando el sistema evalúa la sesión a la hora de envío, antes de preguntar el nivel de fatiga, entonces el mensaje diario incluye una alerta con el motivo climático específico.
- AC-24 (RF-05, RF-07a): Dado un pronóstico cuyo máximo dentro del rango horario preferido del día de la sesión es probabilidad de lluvia >60% o temperatura >32°C, cuando el sistema evalúa la sesión a la hora de envío, antes de preguntar el nivel de fatiga, entonces el mensaje diario incluye como alternativa el primer día, dentro de los 3 días siguientes y sin pasar del domingo de la semana en curso, cuyo rango horario preferido no tenga condición desfavorable; si no existe ninguno, el mensaje dice "No hay una alternativa disponible esta semana".
- AC-25 (RF-07a): Dado un pronóstico con condición desfavorable para la sesión del día y un día alternativo disponible, cuando el sistema emite el mensaje, entonces le pide al usuario que confirme si realiza la sesión o la reprograma, y la sesión original permanece ejecutable mientras el usuario no elija reprogramarla.
- AC-26 (RF-07b): Dado un usuario que recibió el aviso climático y elige reprogramar, cuando el sistema procesa la elección, entonces la sesión X pasa al día alternativo propuesto. Si ese día ya tiene una sesión Y, se compara el volumen: si Y tiene mayor volumen (en km de trote) que X, Y se reemplaza por X; si Y tiene igual o menor volumen que X, se mantiene Y. La sesión descartada (Y o X) no recupera su volumen y desaparece del plan y del historial.
- AC-27 (RF-08): Dado un plan diario generado, cuando el sistema emite el mensaje final, entonces el texto completo (incluidas alertas climáticas y alternativas) tiene una extensión menor o igual a 150 palabras.
- AC-28 (RF-08): Dado un plan diario generado, cuando el sistema emite el mensaje final, entonces el texto contiene tipo de sesión y un rango horario sugerido dentro del rango horario preferido del usuario; si la sesión es de calidad, contiene además el ritmo objetivo; si la sesión tiene bloques de caminata y trote, contiene además la secuencia de caminata y trote.
- AC-29 (RF-09a, RF-09b): Dado un usuario autenticado con una sesión planificada para el día, cuando registra el estado Completada o Parcial/Cortada con un RPE entre 1 y 10, entonces el sistema guarda el registro asociado a esa sesión y lo refleja en el historial del usuario.
- AC-30 (RF-09a, RF-09b): Dado un usuario autenticado con una sesión planificada para el día, cuando la registra como Salteada sin RPE, entonces el sistema guarda el registro asociado a esa sesión y lo refleja en el historial del usuario.
- AC-31 (RF-09b): Dado un usuario que registra una sesión como Completada o Parcial/Cortada sin RPE, cuando el sistema lo valida, entonces responde con código HTTP 422 sin guardar el registro.
- AC-32 (RF-09b): Dado un usuario que registra un RPE fuera del rango 1-10, cuando el sistema lo valida, entonces responde con código HTTP 422 sin guardar el registro.
- AC-33 (RF-09a): Dado una sesión que ya tiene un resultado registrado, cuando el usuario intenta registrar otro resultado para esa misma sesión, entonces el sistema responde con código HTTP 409 sin modificar el registro existente.
- AC-34 (RF-09c): Dado un usuario que registra el resultado de una sesión, cuando envía el registro con o sin notas, entonces el sistema lo guarda en ambos casos y, si hay notas, las muestra en el historial.
- AC-35 (RF-10): Dado un usuario autenticado con un plan semanal activo, cuando solicita ver su cronograma, entonces el sistema muestra las sesiones pasadas, el día actual y las sesiones proyectadas de la semana en curso; las sesiones pasadas sin resultado registrado se muestran como "Sin registrar".
- AC-36 (RF-11): Dado un usuario autenticado con al menos una sesión pasada, cuando solicita ver su historial, entonces el sistema muestra la lista de todas sus sesiones anteriores con su estado (Completada, Parcial/Cortada, Salteada o Pospuesta por clima) y el RPE y las notas asociados a cada una, cuando existan; las sesiones pasadas sin resultado registrado se muestran como "Sin registrar", que no es un estado guardado y cuenta como no Completada.
- AC-37 (RF-03a a RF-03g, RF-09a, RF-09b, RF-09c, RF-10, RF-11): Dado un usuario autenticado con ID X, cuando intenta acceder vía API a un perfil, plan, historial, cronograma o registro de resultados con ID Y (Y≠X), entonces el sistema deniega el acceso retornando código 403 Forbidden, impidiendo cualquier fuga de información.
- AC-38 (RF-09a): Dado un chat de Telegram vinculado al usuario X, cuando intenta registrar el resultado de una sesión de otro usuario Y, entonces el bot rechaza la operación sin revelar ningún dato de Y ni modificar su registro.
- AC-39 (RF-12): Dado un usuario que registra una sesión como Parcial/Cortada con RPE ≥ 7, cuando el sistema genera las sesiones de los dos días de entrenamiento subsiguientes, entonces las reclasifica a intensidad "suave/recuperación", eliminando cualquier sesión de calidad planificada en ese rango.
- AC-40 (RF-13a, RF-13b): Dado un día de sesión con condición climática extrema (temperatura >38°C, tormenta eléctrica o lluvia >80%, dentro del rango horario preferido) sin ningún día alternativo libre de condición desfavorable en los 3 días siguientes y sin pasar del domingo de la semana en curso, cuando el sistema evalúa la sesión a la hora de envío, antes de preguntar el nivel de fatiga, entonces la marca con estado "Pospuesta por clima" y no la ofrece como ejecutable.
- AC-41 (RF-13d): Dado una sesión con estado "Pospuesta por clima", cuando el sistema evalúa si dispara la reclasificación de RF-12, entonces no reclasifica las sesiones subsiguientes a intensidad suave/recuperación, dado que ese estado no equivale a Parcial/Cortada.
- AC-42 (RF-13c, RF-06b): Dado una sesión con estado "Pospuesta por clima", cuando el sistema genera el plan de la semana siguiente, entonces no inserta ni recupera el volumen de esa sesión en otro día, y la base del tope de AC-18 sigue siendo el volumen planificado de la semana anterior, sin descontar la sesión pospuesta.
- AC-43 (RF-13f): Dado que se acumulan 2 o más sesiones con estado "Pospuesta por clima" en la misma semana, cuando el sistema emite el mensaje de posposición, entonces informa explícitamente al usuario la cantidad de sesiones pospuestas de esa semana.
- AC-44 (RF-14): Dado un usuario autenticado que solicita un código de vinculación y lo envía al bot de Telegram dentro de los 15 minutos de generado, cuando el sistema lo valida, entonces asocia ese chat a la cuenta del usuario y el código no puede volver a usarse.
- AC-45 (RF-14): Dado un código de vinculación inválido, ya usado o con más de 15 minutos de generado, cuando se envía al bot de Telegram, entonces el sistema lo rechaza sin asociar el chat a ninguna cuenta.
- AC-46 (RF-14): Dado un chat de Telegram ya vinculado a una cuenta, o una cuenta que ya tiene un chat vinculado, cuando se intenta un segundo vínculo con un código válido, entonces el sistema lo rechaza sin modificar el vínculo existente.
- AC-47 (RF-15, RF-08): Dado un usuario con sesión planificada para el día que no está en estado "Pospuesta por clima", cuando llega la hora de envío, entonces el sistema le pregunta su nivel de fatiga en escala 1-10 y no emite el mensaje diario hasta recibir la respuesta, esperando como máximo 2 horas; transcurridas las 2 horas sin respuesta, emite el mensaje con la sesión planificada sin ajustar por fatiga.
- AC-48 (RF-16): Dado un usuario que reporta fatiga ≥ 8, cuando el sistema define la sesión del día, entonces la sesión asignada es de intensidad "suave/recuperación".
- AC-49 (RF-17): Dado un usuario con Telegram vinculado que solicita restablecer su contraseña desde el bot, cuando el bot le envía un código de un solo uso y el usuario lo envía a la API junto con una contraseña nueva de 8 a 128 caracteres dentro de los 30 minutos, entonces el sistema actualiza el hash Argon2id, responde con código HTTP 200 y el código no puede volver a usarse.
- AC-50 (RF-17): Dado un código de restablecimiento inválido, ya usado o con más de 30 minutos de generado, cuando se envía a la API, entonces el sistema responde con código HTTP 400 sin modificar la contraseña.
- AC-51 (RF-18a): Dado un usuario autenticado con un perfil ya cargado que envía por PUT /profile nuevos datos válidos, cuando luego solicita GET /profile, entonces el sistema devuelve los valores nuevos.
- AC-52 (RF-19): Dado un usuario autenticado que solicita DELETE /profile sin el parámetro confirm=true (ausente o con otro valor), cuando el sistema recibe la solicitud, entonces responde con código HTTP 400 y un mensaje de advertencia de que la eliminación es definitiva, sin borrar nada.
- AC-53 (RF-19): Dado un usuario autenticado que solicita DELETE /profile?confirm=true, cuando el sistema la procesa, entonces borra su perfil, plan, historial y vínculo de Telegram, responde con código HTTP 204, y un login posterior con esas credenciales, o un request con un token aún vigente, responde HTTP 401.
- AC-54 (RF-20): Dado un usuario de nivel novato que en alguna de sus últimas 3 semanas cerradas no tiene al menos 1 sesión Completada o tiene alguna sesión Parcial/Cortada con RPE ≥ 7, cuando envía por PUT /profile un nivel intermedio o avanzado, entonces el sistema responde con código HTTP 422 y el mensaje "Todavía no cumplís las condiciones para cambiar de nivel", sin modificar el perfil.
- AC-55 (RF-20): Dado un usuario de nivel intermedio o avanzado, cuando envía por PUT /profile el nivel novato, entonces el sistema persiste el cambio y responde con código HTTP 200.
- AC-56 (RF-21): Dado un usuario autenticado con perfil completo y chat de Telegram vinculado que no tiene plan para la semana en curso, cuando solicita POST /plan, entonces el sistema genera el plan y responde con código HTTP 201.
- AC-57 (RF-21): Dado un plan generado a mitad de semana, cuando el sistema lo entrega, entonces cubre los días desde la fecha de generación hasta el domingo.
- AC-58 (RF-21): Dado un usuario que ya tiene un plan para la semana en curso, cuando solicita POST /plan, entonces el sistema responde con código HTTP 409 sin generar un plan nuevo.
- AC-59 (RF-22): Dado un usuario con perfil completo y chat de Telegram vinculado, cuando llega el lunes, entonces el sistema genera el plan de esa semana antes de la hora de envío del mensaje diario del usuario.
- AC-60 (RF-22): Dado un usuario con perfil incompleto o sin chat de Telegram vinculado, cuando llega el lunes, entonces el sistema no genera ningún plan para esa semana.
- AC-61 (RF-06g): Dado un usuario que no tuvo plan en la semana anterior, cuando el sistema genera el plan, entonces ninguna sesión supera el tope inicial en km de trote de su nivel (novato 2 km, intermedio 5 km, avanzado 10 km) y el volumen semanal total no supera ese tope multiplicado por la frecuencia cargada.
- AC-62 (RF-06g, RF-21): Dado un usuario cuyo plan de la semana anterior fue parcial (generado a mitad de semana) y que no tiene ninguna semana completa previa, cuando el sistema genera el plan de la semana siguiente, entonces aplica el tope inicial de AC-61 y no el tope de 10% de AC-18.
- AC-63 (RF-06h): Dado un usuario cuya semana anterior no tuvo ninguna sesión Completada, cuando el sistema genera el plan semanal, entonces el volumen semanal total no supera el volumen planificado de la semana anterior.
- AC-64 (RF-07a): Dado un pronóstico con condición desfavorable para la sesión del día y ningún día alternativo disponible, cuando el sistema emite el mensaje, entonces no ofrece la opción de reprogramar y la sesión permanece ejecutable.
- AC-65 (RF-03b, RF-06a): Dado un usuario con frecuencia N cargada, cuando el sistema genera un plan de semana completa, entonces el plan tiene exactamente N sesiones, cada una en un día distinto.
- AC-66 (RF-06a, RF-06b): Dado un usuario cuyo perfil no cambió desde el plan anterior y cuya semana anterior tuvo un plan de semana completa, al menos 1 sesión Completada y no fue de descarga, cuando el sistema genera un plan semanal que no es de descarga, entonces el volumen semanal total es mayor o igual al volumen planificado de la semana anterior y no lo supera en más de 10%.
- AC-67 (RF-06i): Dado un usuario con distancia objetivo D cargada, cuando el sistema genera el plan semanal, entonces ninguna sesión supera D en km de trote.
- AC-68 (RF-13e): Dado un usuario con una sesión del día en estado "Pospuesta por clima", cuando llega la hora de envío, entonces el sistema envía un único mensaje de 150 palabras o menos que informa la posposición y su motivo climático, y no le pregunta su nivel de fatiga.
- AC-69 (RF-09a): Dado un usuario autenticado, cuando intenta registrar el resultado de una sesión cuya fecha no es la del día actual, entonces el sistema responde con código HTTP 422 sin guardar el registro.
- AC-70 (RF-18b): Dado un usuario con un plan vigente que modifica por PUT /profile su nivel, frecuencia, distancia objetivo o ritmo actual, cuando el sistema persiste el cambio, entonces las sesiones del plan vigente no se modifican y el próximo plan generado usa los valores nuevos.
- AC-71 (RF-18c): Dado un usuario que modifica por PUT /profile su ciudad, rango horario preferido u hora de envío, cuando el sistema emite el siguiente mensaje diario, entonces usa los valores nuevos.
- AC-72 (RF-01): Dado un correo con formato inválido o una contraseña de menos de 8 o más de 128 caracteres, cuando el usuario solicita registrarse, entonces el sistema responde con código HTTP 422 sin crear ningún registro.
- AC-73 (RF-02a): Dado un request a un endpoint autenticado sin token, con un token inválido o con un token vencido, cuando el sistema lo recibe, entonces responde con código HTTP 401 sin devolver ningún dato.
- AC-74 (RF-06b, RF-21): Dado un usuario cuyo plan de la semana anterior fue parcial (generado a mitad de semana) y que tiene al menos una semana completa previa, cuando el sistema genera el plan de la semana siguiente, entonces el volumen semanal total no supera en más de 10% el volumen planificado de su última semana completa.
- AC-75 (RF-15): Dado un usuario al que el sistema le preguntó su nivel de fatiga, cuando responde con algo que no es un entero de 1 a 10, entonces el bot vuelve a preguntarle sin emitir el mensaje diario, y la espera máxima de 2 horas de AC-47 sigue contando desde la primera pregunta.

## Fuera de Alcance
Integración nativa directa con hardware vía Bluetooth. · Diagnóstico médico, tratamiento de lesiones o prescripción kinesiológica. · Desarrollo de aplicaciones móviles. · Elaboración de planes de nutrición o dietas personalizadas. · Pasarelas de pago o cobro recurrente de suscripciones. · Canales de entrega distintos de Telegram. · Otros idiomas además del español. · Importación de datos desde Garmin. · Importación de datos desde Strava (incluso con cuenta paga). · Verificación de email. · Múltiples objetivos por usuario. · Desvincular o cambiar el chat de Telegram de una cuenta. · Uso del servicio fuera de Argentina (no se valida la ciudad ni se admiten otras zonas horarias que la de Buenos Aires).

## Riesgos y Dependencias
- Dependencia: API meteorológica · OpenWeatherMap.
- Dependencia: API de Gemini (`gemini-3.5-flash-lite`).
- Dependencia: SQLite.
- Dependencia: API de bots de Telegram.
- Riesgo: Que el LLM sugiera cargas de entrenamiento excesivas para novatos -> mitigación: agregar guardarraíles duros previos a la entrega del plan.
- Riesgo: Consumo excesivo de tokens al pasar historiales largos de entrenamientos -> mitigación: el prompt solo incluye resúmenes semanales y no sesiones individuales.
- Riesgo: Que un usuario nuevo se declare de nivel intermedio o avanzado en su primer alta y se salte los guardarraíles de novato (el nivel es autodeclarado) -> mitigación: ninguna, se acepta como limitación; RF-20 solo protege contra el cambio posterior de novato a otro nivel.
- Riesgo: Que la API de Gemini falle o se demore -> mitigación: avisar que la generación de un nuevo plan no está disponible y entregar el último plan válido (AC-16).
- Riesgo: Que el plan repetido por AC-16 saltee una semana de descarga que correspondía aplicar, o use el nivel, frecuencia, distancia objetivo o ritmo anteriores a una edición del perfil -> mitigación: ninguna, se acepta como limitación; el volumen no aumenta respecto de la semana anterior y el plan siguiente se genera con las reglas y los datos vigentes.
- Riesgo: Que un usuario reduzca su frecuencia y, al mantenerse el volumen semanal, cada sesión se alargue (por ejemplo, de 6 a 2 días por semana); después de la primera semana el único tope por sesión es la distancia objetivo (RF-06i) -> mitigación: ninguna, se acepta como limitación.
